# zg（zvec-grep）的存储设施分析

> **仓库**: `.claude/repo/zvec-grep/`（v0.2.1，浅克隆）
> **类型**: 阅读分析（现状盘点，不含改进建议）
> **分析范围**: 索引数据的落盘形态、目录布局、schema 设计、检索路径
> **证据纪律**: 全部结论附源码路径与行号，可回溯验证

## 一句话结论

zg 的存储设施是 **zvec**——一个进程内（in-process）嵌入式向量/全文检索数据库（npm 包 `@zvec/zvec`，C++ 内核，Node binding），**不是 SQLite、不是独立服务、不是文件目录扫描**。每个工作区把索引存在 `<workspace>/.zvec-grep/` 下的**两个 zvec collection 文件**里：`files.zvec`（文件元数据）+ `index.zvec`（实体片段 + 向量 + 全文倒排）。

## 1. 落盘布局

```
<workspace>/.zvec-grep/          ← 工作区级（索引本体）
├── files.zvec                   ← 文件元数据 collection
└── index.zvec                   ← 实体片段 collection（向量 + FTS）

~/.zvec-grep/                    ← 用户级（全局配置与模型缓存）
├── config.json                  ← 全局默认（embedding 模型、server 等）
└── (模型缓存、daemon 状态)
```

证据：

- 路径布局定义：`src/engine/storage/layout.ts:4-5` 常量 `FILES_ZVEC = "files.zvec"`、`ENTITIES_ZVEC = "index.zvec"`；`:13-22` `resolveWorkspaceIndexStoragePaths()` 把两者拼在同一个 `storagePath` 下
- 工作区索引根：`docs/04-pipeline.md:40` "The workspace index is stored under `<root>/.zvec-grep/`"
- 全局配置：`src/engine/config.ts:127` `resolve(homedir(), ".zvec-grep", "config.json")`
- 架构文档确认双层划分：`docs/05-architecture.md:73-74` "The normal repository index lives under `<workspace>/.zvec-grep/`. Global configuration and daemon state live under `~/.zvec-grep/`"

## 2. 两个 collection 的 schema

### 2.1 `index.zvec` —— 实体片段（核心）

schema 在 `src/engine/storage/zvec.ts:904-957` `createSchema()`。三类字段：

**标量/倒排字段**（`:959-966` `indexedStringField()` 即 `ZVecIndexType.INVERT` 倒排索引）：
- `group`（片段分组，nullable + indexed）、`file_id`（外键，indexed）
- 代码符号维度：`symbol_type` / `symbol_name`（均 indexed）、`symbol_scope` / `symbol_signature` / `symbol_doc` / `symbol_modifiers`（普通字符串）
- Markdown 维度：`heading`、`heading_level`
- 位置：`range_json`（JSON 序列化的行/列范围）、`fragment_index`

**全文检索字段**（`:929-937`）：

```typescript
// src/engine/storage/zvec.ts:929-937
{
  name: ENTITY_TEXT_FIELD,          // "text"
  dataType: ZVecDataType.STRING,
  nullable: false,
  indexParams: {
    indexType: ZVecIndexType.FTS,
    tokenizerName: "jieba",         // 中文分词
    filters: ["lowercase"],
  },
},
```

**向量字段**（`:947-955`）：

```typescript
// src/engine/storage/zvec.ts:947-955
vectors: {
  name: ENTITY_VECTOR_FIELD,        // "embedding"
  dataType: ZVecDataType.VECTOR_FP32,
  dimension: embedding.dimension,   // 随所选 embedding 模型而定
  indexParams: {
    indexType: ZVecIndexType.HNSW,  // 图索引
    metricType: metricToZvec(embedding.metric),  // cosine / dot / L2（:976-993）
  },
},
```

### 2.2 `files.zvec` —— 文件元数据

schema 在 `src/engine/storage/zvec.ts:606-656` `createFilesSchema()`：`file_id` / `absolute_path` / `content_hash` / `kind` / `format`（均 indexed），加 `size_bytes` / `last_modified_time` / `indexed_time` / `entity_count` / `token_count` / `error` 等统计字段。特别地 `entity_ids_json`（`:653`）把该文件对应的全部实体 id 以 JSON 字符串冗余存储——文件级删除/替换时靠它定位旧文档。

## 3. 写入路径（索引时）

`replaceFile()`（`src/engine/storage/zvec.ts:216-256`）是增量更新的原子单元：

1. `markFileDirty`（`:427-438`）—— 先把文件标记为未索引（`indexedTime: null`，清空 entityIds）并持久化
2. `deleteFileDocuments`（`:440-445`）—— `collection.deleteByFilterSync("file_id = ...")` 删旧片段
3. 批量 upsert 新片段（`:258-271` `upsertDocs`，批大小 `ZVEC_UPSERT_BATCH_SIZE = 1024`，`:73`），每条 doc 同时带向量（embedding）与标量字段
4. `persistFile` + `finalizeWrites()`（`:337-344`）—— 需要时对 collection 做 `optimize()`

这个「先标记脏 → 删旧 → 批量写新 → optimize」的顺序保证中断时文件不会处于半索引状态（最坏是回退到"未索引"）。

## 4. 检索路径（查询时）

检索全部走 zvec collection 的 `querySync`，两条路：

- **FTS 检索**（`:303-318` `searchFts`）：`querySync({ fieldName: "text", fts: { matchString: query }, filter, topk })` —— BM25 类关键词检索由 zvec 的 FTS 索引承担（zg 源码里没有自研 BM25 实现；grep `bm25` 在 `src/engine/` 无命中）
- **向量检索**（`:320-335` `searchVector`）：`querySync({ fieldName: "embedding", vector, filter, topk })` —— HNSW ANN

`filter` 是 zvec 的类 SQL 过滤串，由 `buildFilter()`（`:1311-1337`）拼装（`file_id = '...'` / OR 组合），**结构化过滤与向量/全文检索在同一次查询里完成**（混合检索）。

多路结果融合（RRF）在 service 层：`src/engine/service/zvec-grep.ts:2037-2038` `CONTEXT_GROUP_RRF_K = 60`、`:2169` `score + 1 / (K + rank)`；`matchedBy` 汇总为 `fts` / `vector` / `fts+vector` 三态（`:2146-2152`）。ripgrep 精确检索不经过 zvec，是独立通路（`docs/05-architecture.md:8-13` 的 mermaid：`Engine --> RG["Managed ripgrep"]`）。

## 5. 并发与可靠性设计

- **打开重试**：`openZvecCollection()`（`:828-859`）最多 8 次指数退避重试（100ms 起、上限 1s，`:76-78`），只对**锁竞争类错误**重试（`isRetryableZvecOpenError`，`:876-891` 排除 permission/read-only 类）——支持「daemon 持有写锁时 CLI 只读打开」的并发形态
- **只读模式**：构造函数接受 `readOnly`（`:101-140`），所有写操作经 `assertWritable()`（`:451-458`）抛 `READ_ONLY` 错误
- **文件元数据全量列举的分区技巧**：`queryFileMetadataDocs()`（`:554-604`）在文档数超过 `topk` 上限时按 `file_id` 十六进制前缀递归分区查询（`0`→`00`…`0f`…），绕过单查询 topk 限制——这是把「全表扫描」表达成过滤查询的实用手法
- **锁探测**：`canTouchZvecLock()`（`:861-874`）用 `openSync(lockPath, "a")` 试写 `LOCK` 文件判断锁是否可竞争

## 6. 与「提示词日志存储」场景的对照（事实层面）

zg 每个被索引片段存了：文本 + 向量 + FTS 索引 + 倒排标量（符号/文件）+ 位置（range）。检索时三种形态（精确 rg / 关键词 FTS / 语义向量）共用一个存储入口，filter 与检索同查询完成。

其存储依赖 `@zvec/zvec@^0.7.0`（`package.json:77`）——即 [alibaba/zvec](https://github.com/alibaba/zvec)，进程内向量数据库（WAL 持久化、HNSW/IVF 索引、原生 FTS 含 jieba 分词）。zg 自身**没有**实现任何存储引擎逻辑，`src/engine/storage/` 全部代码是 zvec collection 的 schema 定义、读写封装与并发协调。
