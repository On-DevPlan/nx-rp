# 提示词风格与产品打磨要求分析

> 对 2026-10-10 ~ 2026-10-21 期间 `~/.nx-rp/prompts/` 全量提示词日志的离线分析结果。
> 目的：把 901 条真实提示词里隐含的、重复出现的 UI/UX 判据与产品打磨要求**显式化**，
> 让后续任何 agent（或人）在做本项目相关的界面与功能时，可以直接照着执行，不用等用户点名。

## 2. UI/UX 硬性要求

### A. 视觉审美

**A1. 极简克制，禁止大面积纯色与色块**（出现频率最高的 UI 指令）

> "尽可能保证一个页面信息的干净，不要使用大量的纯色，比如说 GitHub 的仓库页只有 git 的按钮，唯一的绿色"
> "不要这么多色块" / "黑白灰 不要色块" / "现在这个 UI 太难看了，以及不要这么多色块"
> "整体设计不要紫色，只需要纯暗夜模式的支持和白夜模式即可，专业，不需要复杂的配色"
> "不要使用蓝色 黑白灰来搭配黑夜模式"
> "不要使用 emoji"
> "用不着 logo 呀"

**A2. 禁假数据、禁占位符**

> "不要什么 example 什么的" / "idp.example.net 别要这种原始地址，所有图都不该包含这个 example 这种字样"
> "请求真实的 api 不要内嵌 json" / "保证所有数据都真实显示"
> "我希望直接产出完整的递归调用的文档压缩包，这种无法直接可用的信息"

**A3. 规范必须可执行、可自动校验**（用户自建的 SVG 规范是范本）

| 维度         | 判据                                                                           | 判据归属                      |
| ------------ | ------------------------------------------------------------------------------ | ----------------------------- |
| 一套坐标     | `viewBox="0 0 24 24"`，不写死 width / height                                 | `svg spec check / spec fix` |
| 一套线条     | `stroke-width="1.8"`（内容有缩放时按倍数折算）+ `linecap/linejoin="round"` | 同上                          |
| 一色跟随主题 | 至少一处 `currentColor`，颜色由外层 CSS 驱动                                 | 同上                          |

> "三者都满足时，同一个 .svg 放在浅色面板、深色底、按钮里都会自动正确，不需要为每种场景再导一份"
> 修正必须**可逐条回退**："改动会写入该风格的编辑历史，可逐条回退"

**A4. 规范要分级，不能一刀切**（用户明确纠过两次）

> "这些就不要放到主 skill 里面了呀，我后续可能存放复杂的 svg 动画，这些要求都是图标相关的要求"
> "有一些 svg 就不需要主题色" / "并且主题色配置的那一行也不需要"

**A5. 长内容自适应，不靠滚动**

> "优化 UI 对长内容的显示，不要上下滑动，直接适配显示全部……所见即所得，自动适配高度"

---

### B. 结构与导航

**B1. 面包屑在左上角 + 多层树 + 分组**（硬性结构要求）

> "对于树结构的资源或者多层的资源需要提供面包屑在左上角"
> "需要支持多层的分组；先重新设计 UI/UX：需要支持面包屑，还有树的目录结构"
> 画廊模式丢失面包屑时："**为什么画廊模式没有面包屑了**"

**B2. 拖拽是基本能力，三种都要**

| 类型                        | 原话                                                                                         |
| --------------------------- | -------------------------------------------------------------------------------------------- |
| 分栏拖拉条（PC 端自定占比） | "对于面板级别，中间需要一个拖拉条在 PC 端，从而让用户自己分配他页面的占比，不要是单纯的卡片" |
| 列表拖放                    | "支持任意的快速拖拽进入" / "平铺 为什么不能支持拖动顺序"                                     |
| 顺序编排                    | "现在的按钮还是过于复杂 并且混乱，最好支持拖拽编排"                                          |

**B3. 多视图且层级不丢**：编辑模式 / 显示模式 / 画廊模式 / 预览模式

> "为什么在画廊模式下文件夹逻辑消失了呀呢？文件夹逻辑应该在画廊逻辑之上呀，一个文件夹下面的东西才展示为画廊"

**B4. 密度可调**

> "画廊模式支持设置一行显示多少个啊，就比如说动画效果的，在图标模式下压根看不清，一行三个才合适"

**B5. CRUD 必须完整，批量操作必须全**

> "所有 web 里面的资源都需要进行完整的增删改查"
> "提供批量操作的时候，需要完成多选全选的功能，保证按钮功能的稳定性"
> "需要支持批量删除呀，目录的"
> 缺失即返工："**还是没有删除分组的功能呀，我操**"

---

### C. 空间与布局

**C1. 不留白、不空卡片、通屏**

> "底部不要那一段小字介绍，直接从上往下通屏，然后方便查看，扩大可视的范围"
> "底部还是有很大一部分空白，图表尽可能充分利用这个页面"
> "优化呀，你现在这个页面一点都不好看，很多空白的背景"
> "不要是单纯的卡片" / "左右面板需要再次比例拖放，而不是固定卡片大小"

**C2. 高度不能被写死**（返工里反复出现）

> "实时预览的高度还是不对" / "实时预览窗口还是高度被固定的"

**C3. 全屏专注模式**：某些场景要脱离全局导航

> "远程输入这个页面为一个全页面，不要让底部的那个导航栏影响建立的全页面"

**C4. 控件要有权重分级**

> "头部的发送和换行按钮做成那种小的控制按钮，不要做成这种大的 tab，没必要做成这么大的纯色，本质只是简单的模式控制"
> "描述 按钮 变成一个主描述加风格列表的模式"
> "点击了子模块 顶部显示就应该切换呀"

**C5. 状态反馈要即时可见**

> "UI 有问题 鼠标下滑就消失" / "什么 toast 都没有显示，只是显示同步中，然后结束" / "这些无法删除" / "为什么还有乱码"

---

### D. 还原度

**D1. 1:1 像素级复刻**是"好"的最高标准

> "尽可能最原始的复制过来……UIUX 尽可能在 nx-ft 1 比 1 的复现"
> "是否实现原始的效果，像素级别的 1 比 1"

**D2. 复用现成范式，而不是重新发明**

> "我只是希望一个边车服务提供授权机制管理主服务，有没有什么机制或者 uiux 可以迁移进入我当前的 nx-as 项目"
> 明确点名对标：nginx-ui 的 diff 预览、npm frontend 的 AuditLog 页、"两家 users/sessions 页的合体"

## 3. 产品打磨方法论（可固化进 SOP）

| 要求                                              | 原话                                                                                                                     |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **量化验收线**                              | "subagent 打分需要大于 98"                                                                                               |
| **循环自检，subagent 每轮重新调研**         | "/rp-loop 无关键字结束 强制 10 轮，每一轮调用 subagent，subagent 必须调研出 5 个真实的需求点，不断扩展进行完善"          |
| **对标外部成熟项目**                        | "调研大型成熟项目和当前的模块的 UIUX，不断优化"                                                                          |
| **Web 改动必须真点**                        | "如果是 web 操作，必须要结合浏览器自动化进行按钮的真实点击"                                                              |
| **文档必须与真实代码对账**                  | "对所有 ref 进行内容质检，检查和真实代码的差异，对于没有任何记忆和参考的段落进行删除，错误案例需要指导性，最好保留 Top5" |
| **规范沉淀为 skill，主 skill 只做 ref map** | "把核心要求放到 reference 里面，主 skill 当中作为 ref map……采用序列 ref 法，A 就是 UI 设计"                            |
| **A 序列只讲审美与评价，不讲怎么写代码**    | "A 序列只需要讲解审美和用户体验，不要管如何写代码，只需要给出评价，什么是垃圾 UIUX，保证绝对的严格"                      |
| **迁移式文档即删**                          | "有标准 SOP 之后删除迁移式、兼容式的文档，后续扩展都基于标准 SOP"                                                        |
| **数据结构只增不减**                        | "尤其是对于结构，应该是只增不减"                                                                                         |
| **边界清晰，不越界**                        | "client 端只需要进行相关的注册管理即可，不需要去给 server 端提供面板，做好区分"                                          |
| **拒绝不可用产物**                          | "我希望直接产出完整的递归调用的文档压缩包，这种无法直接可用的信息"                                                       |
| **导入导出对空填充、不动已有**              | "优先对空白进行填充，不要修改原本的条目结构，也不要修改已经存在的……让用户自己去处理"                                   |

## 4. 提示词表达上最不满的地方

22% 的提示词带明确不满信号。**不满几乎全部指向 AI 交付，而不是需求本身。** 按严重度排序：

### ① AI 只做加法，不做减法（最高频）

> "为什么有多重输入框啊，这些概念有必要这么复杂吗？就是一个文件性质的树形结构，然后进行索引，然后可以访问啊，怎么中间会填写这么多东西呢，对外进行重构啊，现在这个 UI 太难看了"
> "现在的按钮还是过于复杂 并且混乱"

给的是**产品定义**，拿到的是**功能堆积**。过度抽象、层级过深、控件过多。

### ② 该主动实现的没实现，要用户点名

> "**你需要反思一下，为什么之前没有实现，需要要我主动说了才能实现**"
> "当前的项目连 HTML 资源构建的入口都不知道"

### ③ 改坏 / 回归

> "不对啊 现在布局完全混乱了" / "实时预览的高度还是不对" / "UI 有问题 鼠标下滑就消失"

### ④ 规范一刀切，误伤正常场景

> "比如这种 svg 动画在图标体系就不太作用，还会尝试莫名其妙的提醒规范问题"

### ⑤ 静默失败、无反馈

> "什么 toast 都没有显示，只是显示同步中，然后结束" / "这些无法删除" / "为什么还有乱码"

### ⑥ 越界修改全局资产

> "别修改 server-cli-web-scaffold，这是全局的啊，回退"
> "不要覆盖之前的配置，创建新的变量函数" / "私钥不要覆盖" / "不要建立 worktree"
> "不要创建在 nx-tb 里面吗，和 nx-tb 一起分发的"

### ⑦ 文档与代码漂移

> "对所有 ref 进行内容质检，检查和真实代码的差异"（反复提，说明 AI 写的文档大量与实现脱节）

### ⑧ 术语/命名自己擅改、意图被误读

> "名字错了 应该是 sk-source"
> "不对 我的意思是底部不要……"（反复在纠正**意图被误读**）

### ⑨ 抽象空转、只出方案不出成品

> "具体的页面呢 我不要文档"
> "我只是希望一个边车服务提供授权机制管理主服务，有没有什么机制或者 uiux 可以迁移进入我当前的 nx-as 项目"

要的是**可迁移的现成范式**，不是重新设计。

## 5. 交付前自检清单

把上面的不满点转成可机械执行的闸门。**任何界面类改动，提交前逐条过。**

### 减法闸门（对应 ①）

- [ ] 每一个新增输入框 / 面板 / 按钮，都能说出它替代了什么；如果替代不了，就是多余的
- [ ] 层级深度：主视图内不得出现"再点进去才看到主要功能"的情况
- [ ] 控件数量：同类控件不超过 3 个，否则需要归组或收纳

### 完整性闸门（对应 ②⑤）

- [ ] 资源类型清单逐个对照：增 / 删 / 改 / 查 / 批量 / 导入 / 导出 是否都有入口
- [ ] 每个异步操作都有明确终态：成功 toast / 失败 toast / 超时 toast，三者缺一即不合格
- [ ] 每个破坏性操作有确认，且失败有可见文案

### 布局闸门（对应 ③）

- [ ] 面板高度、预览区高度由容器决定，不得写死 px
- [ ] 空白区域要么填内容、要么收进折叠、要么通屏，不留大片空底
- [ ] 浏览器自动化真实点击一遍改动路径，无 console error

### 规范闸门（对应 ④）

- [ ] 规范条目按场景分级（图标 / 插画 / 动画各一套），不跨级告警
- [ ] 规范修复走 `spec fix` 批处理并留下可回退历史

### 边界闸门（对应 ⑥）

- [ ] 未修改 `server-cli-web-scaffold` 等全局 skill
- [ ] 未覆盖既有配置、私钥、变量（新增而非覆盖）
- [ ] 未新建 worktree，未改动任务范围外的目录

### 产物闸门（对应 ⑨）

- [ ] 交付物可直接使用，不是"无法直接可用的信息"
- [ ] 数据来自真实 API，无内嵌 JSON、无 example 占位符
- [ ] 引用的文档与真实代码一致（对账后删除无依据段落）

## 6. 一句话总结

> **UI 要求 = GitHub 式的克制**：黑白灰、少色块、无 emoji、面包屑在左上、树 + 分组 + 拖拽、
> 多视图不丢层级、面板可拖占比、通屏不留白、控件有权重、1:1 像素复刻，
> 且**规范要能自动 check / fix 且可回退**。
>
> **对 AI 的不满 = 只会加不会减、没说就不做、动了不该动的、给不可用的中间产物。**
> 22% 的返工率说明这三点至今没有系统性解决 —— 上面的自检清单就是为解决这三点而设。
