# loop-prompt-craft — 怎么写 loop 的 prompt

循环的成败几乎全部取决于 prompt 质量，而不是模型质量。同一 prompt 会被原样灌回，
所以它要写成**给未来的自己看的交接说明**，而不是一次性的口头指令。

## 一、四条基本要求

### 1. 完成判据必须可验证

❌ 「把 todo API 做好点」
✅ 「REST API 完成，且：CRUD 端点全部工作 / 输入校验就位 / 测试通过（覆盖率 > 80%）/
如果 README 有 API 文档 / 输出 `<promise>COMPLETE</promise>`」

判据说不清 → 循环在错误的信号上停下，或永远不停。

### 2. 分阶段，别一口吃

❌ 「做一个完整的电商平台」
✅ 「Phase 1: 用户认证（JWT + 测试）／Phase 2: 商品目录（列表/搜索 + 测试）／
Phase 3: 购物车（增删 + 测试）。全部完成后输出 `<promise>COMPLETE</promise>`」

每阶段都可独立验证，循环才有中间反馈。

### 3. 把自纠错环写进去

❌ 「实现特性 X」
✅ 「按 TDD 实现特性 X：1) 写失败测试 2) 实现 3) 跑测试 4) 失败则调试修复
5) 需要时重构 6) 重复直到全绿 7) 输出 `<promise>COMPLETE</promise>`」

这类"跑测试 → 看失败 → 修"的环，正是循环最擅长的形态。

### 4. 预写逃逸舱

在 prompt 里明确写出"卡住了怎么办"，否则 agent 可能无限空转或为了脱身说谎：

```
若第 12 轮仍未完成：
  - 记录具体阻塞点（哪个测试/哪个错误）
  - 列出已经尝试过什么、为什么没用
  - 给出替代方案建议
  - **不要输出完成承诺**
```

## 二、承诺词怎么选

- 用**大写下划线**短语：`COMPLETE` / `TESTS GREEN` / `FIXED`
- 避免常见词（`done` / `ok`）—— 模型在正常叙述里也可能说到，且匹配是字面量精确比较
- 一句话提醒会随每轮 `systemMessage` 出现：**只在陈述确实为真时输出**
- 不设承诺词 = 永远不会判定完成，只能靠 `--max-iterations` 收口

## 三、轮次上限怎么定

| 任务类型 | 建议 |
| --- | --- |
| 跑测试到全绿（收敛快） | 10-20 |
| 多阶段特性开发 | 20-40 |
| 探索性重构 | 保守起步（10），观察 `loop log` 后再调 |
| 任何情况 | **不要用 0（无限）**，除非你在场盯着 |

上限是**主保险丝**。承诺词只能表达单一完成条件，无法覆盖"成功 / 卡住 / 需要人介入"
这类多分支结局——所以上限几乎总是必要的。

## 四、nx-rp 特有的三条

### 1. prompt 会被原样灌回，并写进状态文件

`reason` 字段严格等于 prompt 原文（不含轮次等元信息）。好处是 prompt 是稳定前缀，
有利于 KV cache，且每轮任务描述完全一致。反过来说——**写进 prompt 的话会每轮重复出现**，
不要放一次性的寒暄或临时上下文。

### 2. 进度靠文件与 git，不靠对话历史

agent 每轮看到的是**磁盘上的现状**。所以 prompt 里应当引导"先看现状再动手"：

```
先读 package.json 与现有测试，确认当前失败项；再逐项修复。
```

### 3. 每轮的提示语附在 `systemMessage` 里

agent 每轮还会看到一行 `🔄 Loop loop-1 第 3/15 轮 | 完成时输出 <promise>COMPLETE</promise>（仅在确实为真时）`。
不要在 prompt 里重复交代轮次机制。

## 五、反例：什么 prompt 不该布防

- 判据是"感觉对了"—— 无法自动验收
- 需要用户拍板设计取舍 —— 循环里没人可问，agent 会自作主张
- 包含不可逆操作（删数据、发布、付费）—— 循环会把错误放大 N 倍
- 任务本身是一次性的 —— 用普通对话即可
